Overview & how to use

You'll work through two tracks. Track A adds database storage to your existing calc API, starting with one simple insert and ending with a Data Service. Track B uses the same skills on a small banking model: accounts, balances, atomic transfers, idempotency and statements.

  • Do the levels in order. Each one ends with a ✅ checkpoint. Don't move on until it passes.
  • Tick "I finished this level" at the bottom of each level. Your progress is saved in this browser.
  • Debug habit: add <log level="full"/> after any mediator whose result you're unsure about, and read the MI console.
  • Snippets show the important part, not always the full file. Paste them into the right place in your XML, or build the same thing in the VS Code designer and compare.
Suggested one-day plan: morning L0–L4 · after lunch L5–L7 · late afternoon B1–B3 · stretch B4–B5.

The 3 database mediators

Palette itemXML tagWhat it doesWhen to use
DB Report<dbreport>Runs INSERT / UPDATE / DELETE. Doesn't change the message.Audit logs and simple writes
DB Lookup<dblookup>Runs a SELECT and puts the columns of the first row only into properties.Reading one value: a balance, a config value, a cache hit
Call Dataservice<dataServiceCall>Calls a Data Service deployed in the same MI, in-process, without HTTP. The result can go to the body or a property.Production style: multi-row results, transactions, stored procedures, reusable SQL

Rule of thumb

  • One simple write or one single-row read: DB Report / DB Lookup.
  • Multiple rows, business logic, money movement, or SQL shared by many APIs: Data Service (called with Call Dataservice or over HTTP).

Parameter types you'll use

VARCHAR, INTEGER, BIGINT, NUMERIC/DECIMAL (money), TIMESTAMP. An empty string sent to an INTEGER parameter fails, so validate inputs first.

B1 · Bank schema Banking

Goal: a small, realistic core-banking model: accounts, transactions and an audit table.

Why these choices

  • NUMERIC(18,2), never FLOAT/DOUBLE, for money. Floating point gives results like 0.1 + 0.2 = 0.30000000000000004.
  • CHECK (balance >= 0): the database itself refuses an overdraft, even if application code has a bug.
  • reference UNIQUE: the same transfer can never be stored twice (idempotency, see B4).
  • TIMESTAMPTZ: stores time with a timezone. That matters for statements and cut-off times.

Add a second datasource BANK_DB in deployment.toml, the same as L3 but pointing to bankdb.

✅ Checkpoint: SELECT * FROM accounts; shows 3 accounts.

B4 · Idempotency, error mapping & audit Banking

Goal: clean error codes for clients, and an audit row for every attempt, including rejected ones.

Why audit separately?

When transfer_funds raises an exception, its transaction rolls back and nothing is written. A bank still needs a record that someone tried. So write the audit row from MI with a separate DB Report that isn't part of the transfer transaction.

1. Map error codes to HTTP status (in the fault sequence)

Error codeHTTP
INVALID_AMOUNT, SAME_ACCOUNT, CURRENCY_MISMATCH400
FROM_ACCOUNT_NOT_FOUND, TO_ACCOUNT_NOT_FOUND404
INSUFFICIENT_FUNDS, ACCOUNT_NOT_ACTIVE422
anything else (database down, etc.)500, with a generic message. Never show internal errors to clients.

Use a Switch mediator on get-property('ERROR_MESSAGE') with regex cases such as .*INSUFFICIENT_FUNDS.*, and set errorCode and HTTP_SC in each case.

4. Idempotency, end to end

  • The client generates a unique reference (or sends an X-Idempotency-Key header) per transfer.
  • If the network drops and the client retries, the same reference returns DUPLICATE plus the original txnId. The customer is never charged twice.
  • The UNIQUE constraint is the final safety net if two identical requests arrive at the same moment.

Production checklist (banking)

Data & transactions

  • Money is NUMERIC/DECIMAL, never float. The currency is stored next to every amount.
  • All money movement happens in one DB transaction (stored procedure, DSS request-box, or a core banking API). Never use separate DB Report calls.
  • Row locks (FOR UPDATE) are taken in a consistent order to avoid deadlocks.
  • Every write API is idempotent, with a unique reference and a UNIQUE constraint.
  • DB constraints (CHECK, FOREIGN KEY, UNIQUE) are the last line of defence.

Security

  • No credentials in XML or git. Use a datasource, Secure Vault and environment variables.
  • Parameterised SQL only (? / :param), never string concatenation.
  • The DB user has the minimum rights it needs. For example, the API user can EXECUTE the function but can't UPDATE accounts directly.
  • Mask account numbers, card numbers and personal data in logs and audit tables. Never log passwords, PINs, OTPs or tokens.
  • Return generic messages to clients and keep the details in internal logs.

Reliability & performance

  • Size the connection pool, set validationQuery, and set timeouts on endpoints and queries.
  • Index every column you filter or sort on.
  • Paginate every list endpoint and cap the page size.
  • Decide what happens if the audit insert fails: should the client still get its result? Document the decision.
  • For very high volume, consider async audit with a message store/processor or a queue instead of synchronous inserts.

Traceability

  • Store MI's MessageID or a correlation ID in every log and audit row.
  • Use TIMESTAMPTZ and decide on one timezone for reports.
  • Audit rows are append-only: no UPDATE and no DELETE.
